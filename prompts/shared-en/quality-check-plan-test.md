## Quality check — before closing the test plan

Before you switch to `<status:ready_for_tasks>` status, ask yourself:

- **Regression impact (self-containedness inventory, row 10)** — the `<sec:regression_impact>` table of the plan is filled in, or there is an explicit "none". "The implementer will figure it out" is **not** an acceptable answer.
- **A promised test ↔ test case ↔ execution order consistency.** If the plan **promises testing in prose anywhere** — typically in the "handling" sentences of `<sec:risks_and_decisions>` (e.g. *"we verify the fallback logic with a unit test"*) —, then it (a) has a concrete **test case** in the `<sec:test_specification>`, and (b) appears in the **`<sec:execution_order>`** as well. A promise without a test case is a coverage gap.
- **🔴 Do the tests run on the TARGET ENVIRONMENT of the cycle? (EV1–EV5)** — The `**<field:f_target_env>:**` field is present in the `<sec:environment_coords>` section, the `<field:f_environment>` column is filled in **in every row** of the machine run table, and for every non-local category (a) the **command literally contains the target host** (not hidden in a config file), (b) the **prerequisite calls the same host** with a reachability probe, (c) there is **no `localhost`/`127.0.0.1`** either in the command or in the prerequisite. The same holds for the calls of the `TS-NN` scenarios: if the target environment of the cycle is not local, a scenario may call a local address only if its name says so. **A green test does not prove WHERE it was green** — if the target cannot be read out of the command, the quality check FAILS.
- **🔴 Is every test case worked out as a `TS-NN` scenario? (TS1–TS6)** — In the `<sec:plan_test_scenarios>` section there is a block for **every** test case of the spec, with `<field:f_what_we_test>` / `<field:f_prerequisite>` / a step table / `<field:f_cleanup>` lines, and every `DoD-NN` has at least one scenario. Go through it **step by step**: is the HTTP verb, the full endpoint with the port, the headers (including the type of the `Authorization`), the **concrete request body**, the expected status and the key response fields present? For browser E2E, the user interaction **and** the network call belonging to it **and** the visible result? **In the "expected result" cell a "runs successfully" style wording is forbidden** — a concrete, checkable value has to stand there. **If there is only a reference to an earlier cycle, to an existing test file or to the sequence diagram of the spec anywhere, the quality check FAILS** — spell out the steps, then run it again. The `TS-NN` self-test: *"Can an outsider carry out the test reading only this section, and decide whether it succeeded?"*
- **🔴 Is there a `.http` block for a REST scenario? (TS8)** — Every `TS-NN` block that has a REST step also carries a ```http code block (the VSCode REST Client / IntelliJ form), with **the same values** as the `curl` of the step table, referring to the step number, with full headers and body. The table cell speaks to the machine, the `.http` to the human — the two go together, and the gate measures it in both directions.
- **🔴 Does the machine-readable table follow the framework's SCHEMA? (TP4/b)** — The column order is `Category · Type · Prerequisite · Command · Result file · Format · Cleanup · <field:f_environment> · <field:f_phase>` (the last two are optional), the value of `Type` is `gyors`/`nehéz` (these two words are language-independent literals — the `--type` filter of `run-tests.py` matches on their prefixes), and `Result file` is a **path** (not a timeout, not a prose description). **Do not invent your own columns** (`Recipe`, `Timeout`, `Success criteria`): `run-tests.py` reads with **fixed column positions**, so a table with a home-grown schema does not produce an error message, it **uses the wrong cells** — a timeout lands where the command should be, extracting the counts fails silently (TR1 weak evidence) —, and the phase falls back to manual commands, where **not a single `EV` gate runs**. This is how a whole `dev` test category vanished without a trace in a real cycle.
- **🔴 Does the machine-readable table say which PHASE runs it? (PH1)** — In every row the value of the `<field:f_phase>` column is `<status:phase_implement>`, `<status:phase_validate>` or `<status:phase_both>` (an empty cell = `<status:phase_both>`, so an unmarked category runs everywhere). At least one category runs in the `<status:phase_validate>` phase — otherwise `07` runs nothing and `dod-check.py` finds evidence for no `DoD-NN` at all. **A test proving a `DoD-NN` is never `<status:phase_implement>`-only.**
- **🔴 Does every test case say WHAT it verifies? (TD7)** — Not only are the steps concrete, it is also stated **which behaviour** the given test proves and which `DoD-NN` it establishes: in the `<field:f_what_we_test>` line of the `TS-NN` blocks, in the `<field:f_what_it_checks>` column of the unit tables, in the data sheet of the test files, and before every numbered integration/E2E flow. **Repeating the title is not a purpose** ("concurrency test", "testing the login") — a claim has to stand there about which, after the run, it can be decided whether it is true. Without it, at a failure in `07` it cannot be decided whether the code broke or the test is bad.
- **🔴 Did the mechanical gate run, and is its trace in place? (GS2)** — Before the closing, did you actually run `analyze-gate-check.py --plan-only`, did it return `0`, and does its result show in **two places**: in the `**<field:f_gate>:**` line of the `plan.md` header and in the `ANALYZE-GATE: …` line of your phase-closing answer? The status field is self-declared — the entry gate of `04` runs the same gate again (EG1), so an untrue stamp comes to light one phase later anyway.
- **🔴 Has the structure of the test section of the spec leaked over? (TS7)** — **Every** test case of the spec has been **converted** into a standalone `TS-NN` block in the `<sec:plan_test_scenarios>` section. There is no parallel, self-named test section in the plan (`Detailed test cases`, `Sequence descriptions`, `Test case N`) that repeats the test cases of the spec in prose — whatever is not in a `TS-NN` block the gate does not see, the `test-runner` does not run and the manual test plan does not assemble. **Every row of the `<sec:spec_coverage>` table names at least one `TS-NN`** (or the justification of a case that cannot be tested).
- **🔴 Do the test identifiers follow the shared namespace? (TI1)** — The scenarios run from `TS-01`, the cases of the test tables from `TC-01`, **continuously across the cycle**, without gaps or duplicates; there is no `TC-<module>-01` style numbering restarted per file. `tasks.md` refers to these (`— test [TC-01]`), and so does the log of `07` — renumbering an identifier silently breaks the references. The granularity is as big as a test run command can execute **on its own** (`-t`, `-k`).
- **🔴 Does every test file have a data sheet? (TA1)** — Under **every** `#### <test file path>` heading of the `<sec:unit_tests>` / `<sec:integration_tests>` / `<sec:e2e_tests>` there stands the `**<field:f_what_it_checks>:**` (what this test file verifies — the behaviour as a claim, with the `DoD-NN`), the `**<field:f_test_run>:**` (framework + the command narrowed to this one file, runnable verbatim), the `**<field:f_test_fixtures>:**` (fixture/mock/test data with path and content — new files appear in the `<sec:planned_changes>` as well, or `—`) and the `**<field:f_test_cases>:**` (test function name → `TC-ID` / `TS-NN` mapping) line. Designing a new test **does not end with listing the test cases**: if it is not stated with what and how it can be run, the implementer guesses.
- **Self-test:** *"If somebody gets only `plan.md` and `tasks.md` — without the spec, knowledge of the code base and the conversation —, can they develop and test it?"* If they would have to ask back or guess at any point, the plan is incomplete.
- Is the execution order really ordered by dependencies?

- Does the `<sec:test_specification>` section contain test cases for every affected component?
- **Are the tests runnable from the plan alone? (TP3)** — Does it contain the full call of the **token acquisition** (with the concrete test user, with the field to be extracted), the **startup of the stack** (command + health check + cleanup), the build–push–deploy–verify–**rollback** chain of the **custom component**, the **seed** and the **network prerequisite** — all of it as runnable commands, in order? If a prerequisite was built up in an **earlier cycle** and is not in `test-conventions.md`, did you bring it over from the plan of the earlier cycle (TP3/a)?
- **Did the test cases of the spec come over? (TP1)** — Is the `<sec:spec_coverage>` table filled in, and does every case of the spec `<sec:test_specification>` + every `DoD-NN` item map to at least one plan test case (or appear with a justification)? Was the **concrete value** added next to the symbolic coordinates of the spec, and the **concrete call** (verb, endpoint, header, body, expected response) next to the behavior description? Whatever is left out here will not run at the validation.
- **Is the plan self-contained regarding the inlined test recipes (TC1/a)?** — There is no testing step that cannot be carried out without reading `specs/test-conventions.md` (the `test-runner` does not read that file). There is no placeholder, no reference instead of the data.
- Does the Expected output column of every test case contain an HTTP status and an errorCode (where the error matrix of the spec defines it)?
- Do the unit tests appear BEFORE the implementation in the execution order?
- **🔴 You are NOT the one who rewrites the code half.** You have **not modified** the sections written by `03a` (`<sec:goal_and_approach>`, `<sec:affected_components>`, `<sec:environment_coords>`, `<sec:planned_changes>`, `<sec:new_dependencies>`, `<sec:config_build_changes>`, `<sec:schema_artifacts>`): there is no rewritten `[P-…]` entry, no changed coordinate value and no overwritten `<sec:reverse_coverage>` row. Exactly **three** extensions are allowed: (a) a **new row** in the `<sec:reverse_coverage>` table for your own test sections (you do not modify an existing row); (b) a **new `[P-…]` entry** in `<sec:planned_changes>`, **exclusively for a test artifact** (test file, fixture, mock, seed data, test helper), with the mandatory `**<field:f_purpose>:**` line — **never** for production code; (c) a **new paragraph** in `<sec:risks_and_decisions>` about a test-side risk (a flaky scenario, a shared environment, a long run). Anything else that is wrong in the code plan is a `Knn` question in `plan-questions.md` **or** a redirect to `/bs-write-code-plan` — you do not fix it yourself.

If any of these is not satisfied (or something is missing), complete the plan before you close it.

**The self-test for items 13–14:** *"On a fresh machine, reading only this plan, does the test run?"* — if anywhere you would have to say "we already set this up earlier", the plan is incomplete: `test-runner` starts from zero on every run, and it does not read the plans of earlier cycles.

**Why this is a gate and not a checklist row:** experience shows that the most frequent 03 defect is not a bad plan but that **the test cases of the spec simply never reach the plan** — the agent judges them "too detailed" for a plan and leaves them to 04 or to the implementation. But `test-runner` reads neither the spec nor `test-conventions.md`: what is left out here **does not run** at validation, and the gap only surfaces in 07, as a plan gap (TR4) — throwing the whole cycle back here. **In this phase this is the ONLY deliverable** — if a gap remains here, the split was pointless.
