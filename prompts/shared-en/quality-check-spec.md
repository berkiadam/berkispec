## Quality check — at the end of every iteration, ask yourself:

- Is there anything in the spec file that is ambiguous, missing or needs refinement?
- Is there content that belongs into the plan or into the tasks, not into the spec? If yes, delete it.
- Is every "<sec:definition_of_done>" item verifiable and unambiguous?
- **Does every DoD item have a `DoD-NN` identifier (DI1), and are there no two identical numbers?** If one is missing, add it — the per-item stopping counter of `07-validate` builds on this.
- **DoD anti-pattern: is there no "meta" item?** — An item of the *"the description of X is complete"*, *"the test is defined"*, *"its procedure is documented"* kind is **not a DoD**: it checks the existence of a document, not the operation of the system. Every DoD item must be decidable yes/no on **observable behavior**. Bad: *"the test of the procedure of the dev Keycloak SPI update is defined."* Good: *"with the updated SPI the status endpoint returns 200 and an `spi-ok` status."*
- Does the "<sec:out_of_scope>" section prevent scope creep?
- Is the "<sec:referenced_files>" list complete, **and does it contain documentation materials only?** (OpenAPI descriptors, READMEs, schemas, existing spec files, behavior-reference scripts) — `.ts`, `.tsx`, `.js`, `.mjs`, `package.json` and other source files **must not appear**; if they do, delete them. Identifying source files is the task of the plan phase. **Strict rule: concrete source file names must not appear in the prose parts of the specification either (not even in the Risks, the Out of scope or the Test specification sections) — and the same applies to build/deploy commands (`mvn`, `oc`, `kubectl`, `docker`/`podman`, `npm run`), to image names and tags, to registry/namespace/pod/deployment names, and to concrete `host:port` and absolute URL values (KX). These are not to be deleted but to be moved into `plan-input-from-prev.md`. The paths/links of the files must always be relative to the current directory of the file (with as many steps up to the project root as the depth of the folder requires, e.g. `../../apps/legacy-login/README.md`), absolute paths or `file://` scheme links must not appear in them.**
- **Artifact voice (AV1)?** — Is there no skill-voiced meta instruction in the spec (`🔴`, `[!CAUTION]`, "It is forbidden…", "you must check…", "go through…")? Whatever originates from a rule is phrased as a **decision**, and the justification is in the `<sec:risks>` section.
- **Was no detail lost during the filtering (KX2)?** — Compare the `<sec:test_specification>` (and the affected behavior descriptions) with the inputs — `cycle-design-input.md`, `spec-input-from-prev.md`, the roadmap entry — and check it **at the level of the number of steps**: is every step, branch, intermediate check and expected result described there present in the spec? KX could **only** replace a coordinate with a symbolic reference; if the input had 8 steps and the spec has 3 sentences, **the spec is wrong** — restore the level of detail. A merged summary or one of the "the process runs through" kind is not an acceptable substitute. **Rephrasing, refining, spelling out a missing step and a justified reordering are not errors** (KX2/b) — only omission and merging are; if you reordered or inserted a step, you told the user.
- **Did the coordinate filtering (KX) run?** — Did you go through the whole text of the spec, and is there no environment coordinate in it (an absolute URL with a host, `host:port`, an image name, a namespace/pod/deployment, a registry) or procedure description (a build/deploy command, a runbook, a source/artifact file path)? Whatever there was, did you **move** it into `plan-input-from-prev.md` (not delete it), with its full text, and did you **tell the user**? Review the `<sec:test_specification>` section separately as well — that is where a deployment runbook most often creeps in under the heading of a "test".

- **Is every referenced value, structure and datum specified?** — **<field:f_scope>:** this rule applies to the **contract data** (payload fields, header names, error codes, endpoint paths, the name and semantics of configuration parameters) — **not** to the environment coordinates. For a host/port/namespace the correct answer is **not** "let us write in the concrete value", but that **we reference it symbolically, and the value is contained by the plan** (KX). If the spec mentions or references contract data, the following must hold:
  - Its concrete value or an unambiguous generation rule appears in the spec
  - There is at least one example (example request/response, example payload, etc.)
  - Where applicable: a schema is present or referenced (OpenAPI, JSON Schema, Avro, etc.)
  - The implementer should not have to invent anything — if the spec describes a field, they must know what goes into it
- **Is every error branch specified?** — Go through all components and call chains, and check whether every error case is described explicitly. This check is mandatory at the end of every modification iteration. In particular:
  - For REST calls: for every non-200 response the HTTP status code and the errorCode (if any) have to be given, together with the structure of the response body
  - For validation errors: what the condition is, what the return code is, what goes into the response body
  - For external service errors (timeout, 5xx): how the calling component handles it, what it returns to the client
  - If an error branch is not specified, do not fill it in yourself — raise it as an open question
- **An E2E acceptance criterion in the DoD?** — If the cycle introduces any functional behavior (an API, a service, a UI flow), an E2E-level acceptance criterion has to appear in the DoD. The concrete methodology (Playwright, pytest, the level of mocking) is determined by the plan phase — the spec records the expectation, not the implementation. If there is no such item in the DoD, add it.

- **Is `cycle-design-input.md` processed? (CD1)** — If the file exists and contains substantive user content, does every item of it have a traceable fate: incorporated into `spec.md`, moved into `plan-input-from-prev.md`/`tasks-input-from-prev.md`, made an explicit `<sec:out_of_scope>`, or turned into an open `Qnn` question — and did you tell the user about it? Did you leave the file **unchanged**? If the design input and the entry of `roadmap.md` conflict, did that become a `spec-questions.md` question (not a decision of your own)?
- **Is every item of `spec-input-from-prev.md` closed? (IP1)** — If the file exists, no `[ ]` item may remain in it: each one is either incorporated into `spec.md` (the note shows where), or explicitly dropped with a justification. Silently stepping over it is forbidden.
- **Was the valuable information removed from the spec handed over? (IP1)** — If you removed a technical/implementation detail from the spec, did it go into `plan-input-from-prev.md` (not into the bin)?

- **Are the recurring test expectations carried over? (TC1)** — If `specs/test-conventions.md` exists, did you go through sections 2 and 3, and does every item that this cycle takes on as an acceptance criterion appear in the `<sec:test_specification>` (at the level of behavior, referencing the ID of the item)? Did a command, a test file path or a tool name get into the spec? If yes, **delete it** — that belongs into `plan.md`. Are the baseline items invalidated by the cycle marked explicitly for 08?

- **Is a regression check needed?** — If the cycle extends or modifies an existing feature, the <sec:test_specification> section of the spec has to state that the earlier behavior is to be verified with regression tests. This is especially critical if:
  - An existing interface is extended with a new feature or branch (e.g. a new parameter, a new code branch, the introduction of flow detection) — the existing call path must not have broken
  - A shared component changes (a route handler, middleware, shared service) — all of its consumers have to be checked
  - A new behavior is added next to an existing one on the same endpoint or entry point — the two branches have to work independently of each other

- **A contract change → TWO DoD items (descriptor AND code)?** — If the cycle changes a **contract element** (an error code, a field name, an endpoint path, an enum value, a status code), then a **separate DoD item is needed** for (a) the descriptor/schema (OpenAPI, Avro, JSON Schema) **and** for (b) the behavior of the **running code**. A mechanical check: find the DoD item describing the contract change — if it only checks a document/descriptor ("the old code does not appear in the OpenAPI"), **its pair is missing**: "in an error case `<endpoint>` actually returns `<new code>`". An updated descriptor does not prove that the code returns the same.
- **Phasing out (removal) — is the spec's own text clean as well?** — If the cycle **eliminates** a parameter/field/env variable, go through the **own** sections of the spec (schema description, example payload, `<sec:components_behavior>`, `<sec:test_specification>`, DoD), and **delete every occurrence of it** — a typical error is that the DoD states the elimination, but the schema block still lists it. A DoD item is needed that checks the **prohibition** (the old name is not accepted anywhere / the system returns an error for it), not just that "it is no longer mandatory".
- **Rename / project-wide replacement — full coverage in the DoD?** — If the goal of the cycle is **replacing or phasing out** a name (an endpoint, a symbol, an env variable, a file name) **across the whole project** (in such cases the objective typically contains a phrase like "in the whole project" / "everywhere"), then the DoD is not enough if it only lists the *source code*. When writing the spec, go through the artifact classes below, and for every one where the old name **can actually occur**, either have an explicit DoD item, or put it into the **<sec:out_of_scope>** (with a justification). Let no grey zone remain:
  - **Source code** (`src/`, `apps/*/src/`) and the tests belonging to it
  - **Live, non-source documentation:** the root `README.md`, app-level READMEs, `docs/` (architecture, diagrams e.g. `.drawio`), **the skill/agent descriptions under `.agent/`** — these describe the *current* behavior of the system, therefore they are to be rewritten
  - **Build output / generated artifact:** if `dist/` (or another generated folder) is version controlled, a **clean rebuild** should appear in the DoD (the orphan output of the old, renamed source does not get deleted by itself — e.g. `tsc` does not clean it up); or state as Out of scope that `dist/` is not tracked
  - **Configuration and env:** `.env*` templates, compose/CI files, env variable names
  - **Historical artifacts** (the `spec.md`/`test-report`s of closed cycles, dated logs, the past entries of `roadmap.md`): these are **deliberately untouched** — put them into Out of scope explicitly, so that the analyze/review does not report them as an error, and so that nobody rewrites them retrospectively either.
  A distinguishing rule: the **name of the endpoint/symbol** (to be rewritten) ≠ the **concept** using the same word (e.g. "token cache", "Redis Cache" — it stays). The DoD should be phrased precisely enough that these do not get blurred together.
